# GIS 矢量数据 Agent · 优化建议

> 历史记录：网页版（`app/main.py`、`web/`）已随 desktop-only 分支移除，文中相关路径与接口仅作当时状态留存。
>
> 审查时间：2026-10-29  
> 审查范围：`app/`、`web/`、`native/`、`tools/`、入口脚本、依赖与文档  
> 方法：静态阅读 + 对照本机已安装的 GeoPandas 1.2 / Shapely 2.2 接口签名。本文只给建议，没有改动业务代码。

---

## 0. 一句话结论

底子比大多数「GIS + LLM」Demo 扎实：分层清楚、原始图层只读、算子有统一 `Result`、CRS 与编码处理认真、桌面端渲染管线也做了真实性能优化。  
目前最值得投入的不是再加算子，而是四件事：

1. **把「工具契约」变成单一事实源，并做参数校验/预检**（现在同一件事在 `engine`、`TOOL_SPECS`、桌面模板、Web 模板、README 五处各写一遍，已经漂移）。
2. **把自定义算子的「伪沙箱」换成真隔离**（当前可以 `pd.read_pickle()` 执行任意代码，没有超时，还能覆盖内置算子名）。
3. **把一次性规划升级成可纠错的 Agent 循环**（执行失败/缺字段/图层歧义时，能观察结果再修正，而不是直接中断）。
4. **补上长任务与会话的基础设施**（异步任务 + 进度 + 取消、Web 会话隔离、上传/导出临时目录治理）。

---

## 1. 做得好的地方（别改坏）

- `app/` 不依赖 Qt/FastAPI，桌面与 Web 共用同一套引擎与规划器，方向正确。见 [ARCHITECTURE.md](ARCHITECTURE.md)。
- 原始图层只读、算子产出新图层、`Result(ok, message, layer, warnings, data)` 统一返回，便于做步骤卡片与追溯。
- CRS 策略有真实考虑：距离/面积先投到 CGCS2000 3 度带，境外退回 UTM，跨带会提示变形。
- Shapefile 编码择优、字段名 10 字节截断、NaN/Inf 的 JSON 清洗，这些都是踩过坑才会写的细节。
- 桌面端地图不是「能画就行」：图层级缓存、渲染集、按像素容差、亚像素降级、1px 笔宽快速路径，性能数据也有实测记录。
- 规则引擎离线可用 + 大模型可选 + 失败回退，这个降级链对本地工具很关键。
- 选区即输入、撤销、属性表联动、导出视图等交互，产品感是有的。

## 2. P0：正确性与契约问题

### 2.1 工具契约已经漂移，且没有参数校验

同一份算子定义散落在：

- 执行实现：[engine.py](../app/engine.py)
- 给大模型的说明/中文名：[agent.py](../app/agent.py) 的 `TOOL_SPECS` / `TOOL_LABEL`
- 桌面端模板与分组：[native/app.py](../native/app.py)
- Web 端模板：[web/app.js](../web/app.js)
- README 的算子表

已经出现的具体不一致：

| 现象 | 证据 | 影响 |
|---|---|---|
| `bbox_select` 对外声明参数是 `bbox: "x0,y0,x1,y1"`，执行函数签名却是 `xmin, ymin, xmax, ymax` | [agent.py:47](../app/agent.py#L47) vs [engine.py:803](../app/engine.py#L803) | 大模型按说明传 `bbox=` 会直接 `TypeError`；规则解析器也**没有** `bbox_select` 分支，等于这个算子从对话入口不可达 |
| `dedupe` 对外只暴露 `subset`，内部默认 `by_geometry=True` | [agent.py:65](../app/agent.py#L65) vs [engine.py:782](../app/engine.py#L782) | 用户说「按编号去重」时，`subset` 被忽略，实际按几何去重 |
| `dissolve` 内部支持 `agg`，对外完全没暴露 | [engine.py:357](../app/engine.py#L357) | 按字段融合后数值列只取 `first`，用户无法求和/平均 |
| Web/桌面模板里的 `reproject` 固定写 `EPSG:4547` | [web/app.js:23](../web/app.js#L23)、[native/app.py:43](../native/app.py#L43) | 4547 是 CM 114°E；示例数据在成都 104°E，应选 CM 105°E（4544）。模板会把用户带到错带 |
| 规则引擎遇到「CGCS2000 3 度带」硬编码 `4547` | [agent.py:497](../app/agent.py#L497) | 同上；应像 `metric_crs()` 一样按数据中心经度自动选带 |
| Web 端 `min_rect` / `shape_metrics` / `bbox_select` 没有模板 | [web/app.js:15](../web/app.js#L15) 的 `TEMPLATES` | 点工具库只得到「中文名 + 图层名」的兜底句，体验不一致 |
| README 说「超过 5 万要素跳过校验」，代码阈值是 2 万 | [README.md:115](../README.md#L115) vs [engine.py:54](../app/engine.py#L54) | 文档不可信 |
| README/注释说大模型失败静默「2 分钟」，代码是 60 秒 | [README.md:106](../README.md#L106)、[agent.py:276](../app/agent.py#L276) vs [agent.py:736](../app/agent.py#L736) | 同上 |

**建议**：建一个 `app/tool_registry.py`，用 `ToolSpec` 描述 `name / title / group / desc / params(带类型、枚举、默认值、是否必填) / validate / estimate_cost / example`，然后由它生成：

- `OPERATIONS` 的注册表（实现函数仍留在 `engine.py`）
- 大模型 prompt 里的 JSON Schema
- `/api/tools` 返回的完整元数据（Web/桌面共用）
- 中文模板、分组、README 的算子表

执行前用 schema 做一次 `validate_args`，在**任何图层被修改之前**拒绝非法参数。这比在 5 个地方手动同步可靠得多。

### 2.2 几个会算错结果的 bug

#### (a) 线图层的分组统计单位错误

[engine.py:725-727](../app/engine.py#L725-L727)：

```python
top = "、".join(f"{r[key]} {r['sum']/1e6:.3f}km²" ...)
msg = (f"按「{key}」统计{label}：共 {len(agg)} 类，合计 {total/1e6:.4f} km²。")
```

非分组分支已经区分了 `is_line`，但分组分支没有：线图层会显示「总长度 … km²」，而且除以 `1e6` 而不是 `1e3`。表格部分反而是对的，所以同一个结果里文字和表格会互相矛盾。

修法：

```python
div = 1000.0 if is_line else 1e6
unit = "km" if is_line else "km²"
...
```

#### (b) `nearest` 的 `k` 参数实际无效

[engine.py:607-615](../app/engine.py#L607-L615)：

```python
if kk > 1:
    try:
        out = gpd.sjoin(pa, pb, how="left", predicate="nearest", k=kk, distance="distance_m")
    except Exception:
        out = None
if out is None:
    out = gpd.sjoin_nearest(pa, pb, how="left", distance_col="distance_m")
```

已安装的 GeoPandas 1.2 中，`sjoin()` 的合法 predicate 不包含 `"nearest"`，也不接受 `k` / 距离列参数；这一行会抛异常并被 `except` 吞掉，然后永远走 `k=1` 的 `sjoin_nearest`。也就是：

- 用户说「找最近 3 条道路」，只会返回 1 条；
- 没有 warning，静默降级。

**建议**：要么暂时删掉 `k` 参数并明确只支持最近 1 个；要么用 `shapely.STRtree.query_nearest` / KDTree 实现真正的 k 近邻。无论哪种，都不要用裸 `except Exception` 掩盖接口不匹配。

#### (c) `sjoin` 静默丢字段

[engine.py:590](../app/engine.py#L590)：

```python
gb = gb.drop(columns=[c for c in gb.columns if c in ga.columns and c != gb.geometry.name], errors="ignore")
```

两个图层有同名字段（很常见：`名称`、`代码`、`id`）时，右图层的同名字段会被整列丢掉，且没有任何 warning。用户看到的「空间连接」结果会缺一半属性。

**建议**：用 `lsuffix` / `rsuffix` 保留双方字段，或者只对冲突列加 `_b` 后缀，并在 `warnings` 里说明。

#### (d) Web 端会丢掉大模型的自然语言回复

[native/app.py:1291-1294](../native/app.py#L1291-L1294) 正确处理了「模型只回 reply、不给 plan」的情况；但 [main.py:272-281](../app/main.py#L272-L281) 没有：

```python
if out and out.get("plan"):
    plan, source = out["plan"], "llm"
    note = out.get("reply") or ""
elif out and out.get("error"):
    note = out["error"]
if not plan:
    plan = planner.rule_plan(msg, body.current)
```

模型返回 `{"plan": [], "reply": "这个图层适合做..."}` 时，`reply` 被忽略，规则引擎也拆不出步骤，最后用户看到的是模板句「这句我还拆不出可执行的步骤」。这是一个直接拉低 Agent 体验的问题。

**建议**：与桌面端对齐，`out["reply"] and not out["plan"]` 时直接作为聊天回复返回；同时把 `planner` 标成 `llm`。

#### (e) `run_plan` 的 `$prev` 解析在 try 之外，部分成功会丢失

[agent.py:819-832](../app/agent.py#L819-L832) 的图层解析发生在 `try` 之前，`$prev` 没有上一步时会 `raise ValueError`。异常传到 `main.chat` 后，之前已经成功执行的步骤和已生成的图层都还在 store 里，但调用方只拿到一个「规划失败」的通用错误，步骤卡片和撤销登记都会丢。

**建议**：

- 把参数解析移进 per-step `try`；
- 或者先做一次 `validate_plan(store, plan)` 预检（工具名、图层引用、必填参数、`$prev` 链），预检不过就**一步都不执行**；
- 返回 `steps` 时始终包含已完成的步骤。

#### (f) CRS 的两个真问题

1. **缺 CRS 时静默按 4326 处理**：[engine.py:158-163](../app/engine.py#L158-L163)、[io_utils.py:43-44](../app/io_utils.py#L43-L44)。  
   Shapefile 缺 `.prj` 非常常见，如果坐标其实是投影米制（例如 `(500000, 3300000)`），按经纬度处理后所有距离/面积都会离谱，而且只给一条 warning，用户很容易忽略。  
   **建议**：无 CRS 且坐标明显超出 `[-180,180]/[-90,90]` 时，拒绝距离/面积运算并要求用户指定 CRS；或在导入时弹「请选择坐标系」。不要把 `set_crs(4326)` 当成默认修复。

2. **投影坐标系不检查单位**：[engine.py:182-183](../app/engine.py#L182-L183) 对任何 projected CRS 直接返回，但 `_buffer` / `_simplify` 把 `distance` 当米。若数据是 `EPSG:2226`（英尺）之类，缓冲 500 米会被当成 500 英尺。  
   **建议**：用 `crs.axis_info[0].unit_conversion_factor` 判断；非米制时先转米制或明确拒绝。

#### (g) 叠加类算子没有统一做几何修复

`_buffer` / `_clip` 调用了 `_fix_geom`，但 `_intersect` / `_union` / `_erase` / `_dissolve` / `_sjoin` / `_nearest` / `_voronoi` 没有。无效几何（自相交、环未闭合）在 `gpd.overlay` 里可能直接抛 GEOS 异常，用户看到的是底层英文错误。

**建议**：做一个 `@prepared` 装饰器或 `_prepare(lay)`，统一做：

1. `_ensure_crs`
2. `make_valid` + 计数
3. 空几何清理
4. 记录 warning

所有算子入口都走它。顺便解决各算子重复代码的问题。

#### (h) 自定义算子会修改原始图层，破坏「只读」不变量

[engine.py:864](../app/engine.py#L864)：

```python
gdf, w = _ensure_crs(lay.gdf)
out, msg = custom_ops.run_op(spec, gdf, args)
```

当图层已有 CRS 时，`_ensure_crs` 直接返回原对象；自定义算子里的 `gdf["x"] = ...` 会改到 store 里的原图层。更糟的是 `Layer.meta()` 有缓存（[engine.py:86-108](../app/engine.py#L86-L108)），字段列表/要素数不会刷新，后续 UI 和规划器看到的是旧 schema。

**建议**：`custom_ops.run_op(spec, lay.gdf.copy(), args)`；试跑也用 `.head(200).copy()`。

### 2.3 自定义算子的安全边界被高估了

`custom_ops.py` 的 AST 检查挡住了 `import` / `while` / `open` / `eval` / `__dunder__`，但**没有限制模块方法**。生成的代码里这些都仍然合法：

```python
pd.read_pickle("data/operators/x.json")   # 反序列化可执行任意代码
gpd.read_file("http://...")               # SSRF / 读本地文件
gdf.to_file("C:/...")                      # 任意写文件
np.frombuffer(...)                         # 大内存分配
for _ in range(10**12): ...                # while 被禁了，但 for 可以跑很久
```

同时：

- 没有执行超时；
- 没有内存/CPU 限制；
- `install()` 直接 `OPERATIONS[spec["name"]] = ...`（[custom_ops.py:198](../app/custom_ops.py#L198)），一个叫 `buffer` 的生成算子会覆盖内置 `buffer`；
- `remove()` 只删文件，不注销运行时的 `OPERATIONS` / `TOOL_SPECS` / `TOOL_LABEL`（[custom_ops.py:216-223](../app/custom_ops.py#L216-L223)），删完当前会话仍然能调用；
- 预览弹窗写着「禁止文件与网络访问」（[native/dialogs.py:387](../native/dialogs.py#L387)），与事实不符。

**建议（按投入排序）**：

1. **最低成本**：加 `subprocess` / `multiprocessing` 隔离，设置超时（如 10s）和内存上限（Windows Job Object / `resource.setrlimit`），父进程只接收序列化结果。代码生成场景非常适合这种「一次性执行」。
2. **中等成本**：不要注入整个 `pd`/`gpd`/`shapely` 模块，改成注入一个受限的 facade（只暴露 `GeoDataFrame`、`GeoSeries`、`shapely.area/length/intersection/...` 等白名单函数）；禁止 `pd.read_*` / `to_*` / `gpd.read_file` / `to_file`。
3. **必须做**：`name` 与内置算子冲突时拒绝，或自动加 `custom_` 前缀；`remove` 同步清理三张表。
4. **随手做**：`compile_op` 按代码 hash 缓存，避免每次执行都 `compile + exec`。

## 3. P0：会话、并发与临时文件

### 3.1 Web 是全局单例，多标签页会互相串数据

[main.py:49-52](../app/main.py#L49-L52)：

```python
store = Store()
planner = Planner(store)
history: list[dict] = []
IMPORT_JOBS: dict[str, dict] = {}
```

FastAPI 的同步端点在线程池里执行；两个标签页同时 `/api/chat` 时：

- 两个请求共享同一个 `store`，一个在跑 `overlay`，另一个在读图层列表；
- `history` 混在一起，A 的指令会进入 B 的上下文；
- `Planner._llm_fail_at` 也是全局的，一个用户的网络错误会让所有用户静默 60 秒；
- 长算子占住线程池线程，多个请求叠加会拖慢甚至耗尽线程池。

**建议**：

- 近期：加 `threading.RLock`，所有会改 `store` / `history` 的端点串行化；至少保证「一个聊天请求执行期间不并行改图层」。
- 中期：按 cookie/session 分 `Store` 与 `history`（`SessionState`），`IMPORT_JOBS` 也挂到 session 上；加 TTL 清理。
- 长期：把空间运算做成后台 job（见 4.2），HTTP 只负责提交/查询/取消。

### 3.2 上传、解压、导出都会泄漏磁盘

这是一个已经在工作区里能看到的问题：`data/uploads/2415b1ef/...` 还留着上次上传解压出来的 Shapefile。

具体路径：

| 位置 | 问题 |
|---|---|
| [main.py:145-149](../app/main.py#L145-L149) | 每次上传建一个 `UPLOADS/<uuid>`，单文件成功载入后**从不删除** |
| [io_utils.py:145-160](../app/io_utils.py#L145-L160) | 多图层 zip 的 `x_*` 目录靠 `/api/import` 清理；用户关掉弹窗就永久残留 |
| [main.py:198-226](../app/main.py#L198-L226) | `IMPORT_JOBS` 只 `pop` 不设 TTL，也没有进程退出清理 |
| [main.py:337-344](../app/main.py#L337-L344) | 每次导出 `tempfile.mkdtemp()`，`FileResponse` 发完不删 |
| [main.py:387-392](../app/main.py#L387-L392) | `/api/reset` 清图层/历史，但不清上传目录和 `IMPORT_JOBS` |

**建议**：

- `try/finally` 清理单文件上传的 work 目录；
- 多图层 job 加 `created_at`，后台线程/请求时清理超过 30 分钟的；
- 导出用 `BackgroundTask(shutil.rmtree, tmp)`；
- `/api/reset` 一并清理；
- 加一个「清理缓存」入口，显示占用空间。

### 3.3 上传没有大小/数量/解压比限制

[main.py:139-190](../app/main.py#L139-L190) 只检查扩展名，没有 `Content-Length` 上限；`extract_zip` 直接 `extractall`，没有总解压大小、文件数、压缩比限制。一个 zip bomb 可以把磁盘写满。

说明：Python 标准库 `zipfile` 会清理 `..` 和绝对路径，所以**不要**把它当成 Zip Slip；真正缺的是 zip bomb / 超大文件防护。

**建议**：

- 上传上限（如 500MB）与解压后上限（如 2GB）、文件数上限（如 1000）；
- 先遍历 `ZipInfo` 累加 `file_size`，超限直接拒绝；
- 只解压白名单扩展名，且每个目标路径 `resolve()` 后确认在根目录内（双保险）。

### 3.4 Web 端 Shapefile 多文件上传是坏的

[main.py:151-159](../app/main.py#L151-L159) 要求 `.shp` 同目录有 `.dbf/.shx`，但 [web/app.js:237-257](../web/app.js#L237-L257) 是**逐个文件**发 `/api/upload`，每个文件落在不同的 UUID 目录。结果：

- 用户同时选 `道路.shp / 道路.dbf / 道路.shx`，`.shp` 请求永远看不到 `.dbf/.shx`，必然 400；
- 界面又明确接受 `.shp`，所以这是一个稳定复现的坏路径。

**建议**：Web 端改成一次 multipart 请求带多个文件，按 stem 分组落到同一目录；或者从 Web 的 `accept` 里去掉 `.shp`，明确提示「请打包成 zip」。桌面端是按路径读取的，不受影响。

### 3.5 API Key 的落盘保护

[config.py:77-81](../app/config.py#L77-L81) 直接把 key 明文写 `data/settings.json`，没有原子写、没有权限收紧。Windows 本地单用户问题不大，但：

- 多用户机器/共享目录上，其他用户可能读到；
- 写到一半崩溃会留下半截 JSON，下次 `load_cfg` 静默失败，用户以为 key 丢了。

**建议**：临时文件 + `os.replace` 原子写；POSIX `chmod 600`；Windows 可用 DPAPI 或至少依赖用户目录 ACL；文档里明确「key 是明文，别放在共享目录」。

## 4. P1：Agent 能力（这是「Agent」和「自然语言命令行」的分水岭）

### 4.1 从 one-shot 规划升级为 plan → act → observe → repair

现在 [main.py:271-324](../app/main.py#L271-L324) / [agent.py:733-798](../app/agent.py#L733-L798) 是：

1. 把用户话 + 图层 schema 发给模型；
2. 模型一次性给出完整 plan；
3. `run_plan` 顺序执行；
4. 任一步失败 → `break`，把错误原样返回。

这有两个明显短板：

- **模型看不到执行结果**：它规划时不知道「字段其实叫 `用地类型` 而不是 `类型`」「裁剪面不是面图层」「上一步结果只有 0 个要素」；
- **失败后不会修正**：`run_plan` 直接中断，用户只能自己重说一遍。

**建议**：加一个受控的 Agent 循环（最大 3~5 步，避免成本和死循环）：

```
plan_step = llm.plan(goal, schema)
for i in range(max_steps):
    result = execute(plan_step)
    if result.ok: 
        if done: break
        plan_step = llm.next(goal, history, result.summary, schema_after)
    else:
        plan_step = llm.repair(goal, failed_step, error, available_layers, fields)
```

关键设计：

- 只把**结构化摘要**回灌给模型（要素数、字段变化、warning、错误类型），不要把整个 GeoDataFrame 塞进 prompt；
- 修复次数有上限，超过就把「最后一步错误 + 建议」返回给用户；
- 每一步执行前做 schema 校验，执行后更新 schema（尤其 `shape_metrics` / `field_calc` 会新增字段）；
- 对「删除/覆盖/超大计算」保留用户确认。

这会比现在多花一些 token，但能显著提升「一句话完成复杂任务」的成功率。

### 4.2 长任务异步化 + 进度 + 取消

`/api/chat` 是同步端点，一个 500k 要素的 overlay 可能跑几十秒到几分钟。浏览器 `fetch` 没有超时，但：

- uvicorn 线程被占住；
- 用户看不到「第几步/多少要素」；
- 关掉页面任务还在跑；
- 多标签页会叠加。

**建议**：

- `POST /api/jobs` 返回 `job_id`；`GET /api/jobs/{id}` 查状态；`DELETE /api/jobs/{id}` 取消；
- 用 `asyncio.Queue` / 线程 + `threading.Event` 做取消令牌，在算子循环/geopandas 调用之间检查；
- 前端用 SSE（`text/event-stream`）或轮询展示步骤进度；
- 桌面端已经有 `Worker` + 计时器，可以复用同一套「步骤事件」协议。

### 4.3 多轮指代与澄清

现在规则引擎完全不看历史；大模型看 `history[-6:]`，但：

- 「再大一点」「换成 1 公里」「用刚才那个结果」这类指代没有稳定的槽位；
- 图层歧义时 `_resolve_target` 直接取「最近创建的图层」（[agent.py:349-360](../app/agent.py#L349-L360)），不询问；
- 字段名不完全匹配时（「按类型融合」而字段叫「用地类型」）直接 `by=None`，静默融合全部。

**建议**：

- 维护 `last_plan / last_args / last_result_layer`，支持「它 / 刚才 / 上一步 / 再…」；
- 图层歧义且无当前选中时，返回一个澄清问题 + 候选列表（前端渲染成可点按钮）；
- 字段模糊匹配（`用地类型` vs `类型`）用 `difflib` / 别名表，匹配不到就列出候选字段，不要静默改变语义。

### 4.4 大模型调用的健壮性

| 问题 | 证据 | 建议 |

现在有 `tools/test_*.py`，但主要是 UI/渲染冒烟；没有「一句话 → 期望算子链」的回归集。改提示词或加算子后，无法量化是否变好。

**建议**：加 `tools/eval_planner.py`：

- 50~100 条真实中文指令，标注期望 `tool` 序列（不要求参数完全一致）；
- 支持 `--planner rule|llm`，输出 exact / partial / failed、平均耗时、token；

这是「Agent 应用」最值得补的工程资产之一。

## 5. P1：性能与大数据

### 5.1 后端

### 5.2 Web 地图是「每帧全量重建」

[web/map.js:265-294](../web/map.js#L265-L294) 的 `draw()` 每次：

- 遍历所有图层的所有要素；
- 对每个坐标做 `project` + `toScreen`；
- 每个要素新建 `Path2D`；
- 悬停变化、拖拽、每次 `mousemove` 都可能触发整帧。

30k 要素时还能忍，再大就会明显卡；而且没有视口裁剪、没有简化、没有图层级缓存。桌面端的 `mapview.py` 已经有成熟方案（`_RenderSet`、`_LayerCache`、按视口筛要素、按像素容差简化、亚像素降点），Web 端可以借鉴其中最便宜的三条：

1. **视口裁剪**：先用要素 bbox 与当前视口求交，屏幕外的不建 path；
2. **按比例尺简化**：屏幕尺寸 < 1.5px 的面降为点，线做 Douglas-Peucker（或直接抽稀）；
3. **图层级离屏缓存**：每个图层画到 `OffscreenCanvas`，视图平移时直接贴图；缩放/显隐才重建。

另外：

- [web/map.js:225-240](../web/map.js#L225-L240) 的 `_hit` 在每次悬停时线性遍历所有 path，30k 要素会明显延迟；用 bbox 预筛 + 空间索引，或者用「颜色拾取」的离屏画布。
- [web/map.js:98-100](../web/map.js#L98-L100) `screenToLonLat` 依赖 `Object.values` 的属性顺序，建议显式解构，避免以后重构踩坑。
- [web/map.js:252-255](../web/map.js#L252-L255) `_pick` 在 `window` 的 `mouseup` 上取 `e.offsetX`，事件目标不一定是 canvas，坐标可能偏；应记录最后一次 canvas 内坐标，或用 `getBoundingClientRect` 换算。
- 没有触摸/指针事件，移动端不可用。

### 5.3 Web 端内存与截断提示

[web/app.js:137-142](../web/app.js#L137-L142) 的 `state.geo` 永久缓存每个图层的完整 GeoJSON；删除图层/切换项目时没有 eviction。  
更重要的是 [main.py:100](../app/main.py#L100) 已经返回 `_meta.truncated`，但前端完全没读：用户看到的地图可能只有前 3 万要素，却以为看到了全部。

**建议**：

- 在图层条目/状态栏显示「仅显示前 3 万要素，统计基于全量」；
- 图层删除时 `delete state.geo[id]`；
- 大图层默认懒加载（只有可见时才 fetch），或先请求 bbox/简化版本。

### 5.4 桌面端属性表会复制整表

[dialogs.py:30-37](../native/dialogs.py#L30-L37) 打开属性表时：

```python
self._data = g.drop(columns=[g.geometry.name]).reset_index(drop=True)
```

对 50 万行 × 十多个字段的图层，这是几百 MB 的复制，而且发生在 GUI 线程。加上 [dialogs.py:94-106](../native/dialogs.py#L94-L106) 每次输入筛选都对所有列 `astype(str).str.contains` 全表扫描，77 万行的道路图层会明显卡顿。

**建议**：用 `QAbstractTableModel` 按页从 `gdf` 取数（`iloc`），筛选/排序用 pandas 在后台线程算，输入加 250ms 防抖；至少不要一开始就复制整表。

### 5.5 内存模型

所有图层都常驻内存（`Store.layers` 持有完整 GeoDataFrame）。派生层越多，内存越接近线性增长；50 万要素做 5 步分析就可能 OOM。

**建议**：

- 图层落盘为 GeoParquet（`data/cache/<layer_id>.parquet`），`Store` 只保留元信息 + 最近使用的 N 层；
- 算子执行时按需加载，结果写回缓存；
- 给「当前项目」设内存预算，超出时提示或自动驱逐；
- Web 端同理，服务端只缓存 GeoJSON 的简化版本/分页。

这会让「关掉窗口就丢数据」的已知边界一起解决，也能顺带做项目保存。

## 6. P2：产品与体验

### 6.1 项目持久化

现在关窗即清空（README 已列为已知边界）。对 GIS 用户，这是最大的心理门槛之一。

**建议**：一个轻量 `.gisproj`（JSON）：图层列表（指向 GeoParquet/GeoJSON 缓存）、当前视图、图层顺序/显隐/颜色、对话历史、自定义算子版本。支持「最近项目 / 自动保存 / 另存为」。不需要数据库。

### 6.2 Web 与桌面功能对齐

Web 目前缺少：自定义算子、撤销、重命名/复制/删除、图层排序、属性表分页/排序/筛选、导出视图、键盘快捷键、选区。  
要么补齐，要么在 README/UI 明确标「Web 是只读预览版」，避免用户按 README 的桌面功能去期待。

### 6.3 图层符号化

当前每个图层只有一种颜色。GIS 用户很快就会想要：

- 按字段分类着色（categorized）
- 按数值分级（graduated）
- 透明度、线宽、点大小
- 标注（label）与标注避让
- 图例分组/折叠

这比再加几个空间算子更能提升「可直接出图」的价值。

### 6.4 导出与报告

- 导出格式：GeoJSON / GPKG / SHP(zip) / CSV 已有；可加 **GeoParquet**（大图层）、**KML**（读支持但写不支持）、**DXF**（规划/CAD 用户）。
- 批量导出：一次导出多个图层/多个格式。
- 报告：当前「导出视图 PNG」很好用；可以进一步生成「地图 + 统计表 + 步骤记录」的 PDF/HTML 报告，GIS 项目汇报很常用。
- 导出时选择 CRS / 字段子集 / 仅选中要素。

### 6.5 地图交互

- 量距/量面积工具；
- 坐标定位（输入经纬度跳转）；
- 书签/视图历史；
- 可选底图（离线瓦片或在线瓦片，做成开关，保持默认离线）；
- 触摸/触控板手势；
- Web 端框选/点选。

### 6.6 可访问性与细节

- 图标按钮加 `aria-label` / tooltip；键盘可聚焦；
- 颜色不是唯一区分手段（图例加线型/符号）；
- 长图层名省略 + 悬浮全名（桌面已有 `ElideLabel`，Web 没有）；
- 错误提示区分「用户输入问题」和「程序 bug」，后者带 request id 方便排查。

## 7. 工程化

### 7.1 测试

- `tools/test_*.py` 里多数脚本失败时**不会返回非零退出码**，例如 [test_custom_op.py:98](../tools/test_custom_op.py#L98) 只 `print("FAIL")`。CI 会误判为通过。

- 没有覆盖本次发现的回归点。

**建议**：

1. 每个脚本失败时 `sys.exit(1)`（一行改动）；
2. 加 `pytest` + `conftest.py`，把 Qt offscreen 设置集中；
3. 纯引擎/规划器测试不依赖 Qt：`tests/test_engine.py`、`tests/test_planner.py`；
4. 必加用例：
   - 线图层分组统计单位；
   - `nearest(k=3)` 返回 3 条；
   - `bbox_select` 按 `bbox` 字符串调用；
   - `dedupe(subset=...)` 按字段去重；
   - `sjoin` 同名字段保留；
   - 缺 CRS 的投影数据不静默算面积；
   - Web 上传 `.shp + .dbf + .shx`；
   - 多标签页并发 chat（至少加锁后不串数据）。
5. CI：Windows + Ubuntu，Python 3.11/3.13，跑 engine/planner 测试 + `pytest`；Qt 测试可以只在 Windows 跑。

### 7.2 日志与可观测性

- Web 端没有 logging 配置；桌面端 `native_app.py` 只在 fatal 时写 `data/app.log`，与 README「数据载入、运算的日志在 data\app.log」不符（[README.md:24](../README.md#L24)）。
- 没有 request id、算子耗时、要素数、warning 的结构化记录。

**建议**：

- `logging` + `RotatingFileHandler`，统一格式 `time level request_id tool elapsed features_in/out warnings`；
- `/api/health` 返回版本号、启动时间、图层数、内存占用；
- LLM 调用记录 `usage`（prompt/completion tokens）与 `model`；
- 前端错误上报可先不做，但后端 5xx 必须带 request id 写日志。

### 7.3 依赖与打包

- `requirements.txt` 只有下界/大范围，`pandas>=2.2,<4` 跨越了 3.x 的大版本；建议生成 lock（`pip-compile` / `uv lock`）并固定实测组合。
- `启动.bat` 首次运行直接联网 `pip install`，离线/弱网环境会失败；可提供 wheel 包/离线安装说明。
- 没有版本号；`/api/health`、窗口标题、导出文件名都可以带版本。
- 若要做正式分发：PyInstaller / Nuitka 打包、代码签名、单实例锁、崩溃日志收集（opt-in）。
- 没有 LICENSE 文件（如果要开源/分发）。

### 7.4 代码结构

- `_parse_clause` 是一个 170 行的 if 链，新增说法只能继续加分支；建议改成「规则表」：`(pattern, handler)` 列表，按优先级匹配，handler 只负责抽参数。这样也更容易写单元测试。
- `_parse_clause` 里有**两个完全相同的 `filter` 分支**（[agent.py:604-607](../app/agent.py#L604-L607) 与 [agent.py:628-631](../app/agent.py#L628-L631)），第二个永远不会执行。
- `_points_along` 是未注册的 `NotImplementedError` 死代码（[engine.py:552](../app/engine.py#L552)）。
- `_is_categorical` 定义了但没有被使用（[agent.py:666](../app/agent.py#L666)）。
- `native/mapview.py` 2000+ 行、`native/app.py` 1600+ 行，建议按「渲染集/构建/交互/标注」拆模块；不急于一次拆完，但新功能不要再往 `app.py` 里堆。
- 大量 `except Exception: pass` 会把真实 bug 藏起来（例如 `_nearest` 的 k 分支）。至少记录 `logger.debug(..., exc_info=True)`，或在开发模式重新抛出。

### 7.5 文档与事实校准

建议把 README 里的数字/承诺与代码对齐，或者反过来让代码满足文档：

- 2 万 vs 5 万要素阈值；
- 60 秒 vs 2 分钟冷却；
- 日志位置；
- 算子数量（Web 实际展示 24 个，因为 `describe` 被排除；HTML 初始写 22）；

文档是用户信任的一部分；这些不一致会让人怀疑「生产规范」章节的其他结论。
